# Репликация бакетов

[English version](replication.md)

Exordos управляет Bucket replication RustFS через отдельные **цели** и
**правила**. У исходного бакета может быть несколько целей, у каждой цели —
несколько правил с разными префиксами, тегами и настройками удаления. Приёмником
может быть RustFS или совместимый S3. Он должен поддерживать версионирование и
запросы репликации RustFS: совместимость с S3 сама по себе не гарантирует
сохранение версий и метаданных. Интеграционный тест использует RustFS 1.0.1
с обеих сторон.

Репликация копирует изменения объектов. Базу Exordos, IAM-пользователей, ключи,
политики и настройки инстанса нужно сохранять отдельно для восстановления.
Перенос удаления конкретных версий может уничтожить историю бекапа.
Используйте отдельные ключи приёмника и настройте retention и lifecycle так,
чтобы сохранить нужное окно восстановления.

## Пути API

Все идентификаторы в путях — UUID ресурсов, включая исходный бакет.
Аутентификация и выбор проекта совпадают с остальными S3-ресурсами.

| Коллекция | Путь |
| --- | --- |
| Цели | `/v1/types/s3/instances/{instance}/buckets/{bucket}/replication_targets` |
| Правила | `/v1/types/s3/instances/{instance}/buckets/{bucket}/replication_targets/{target}/rules` |

Коллекции поддерживают `POST` и `GET`. Для `GET`, `PUT` (частичного обновления)
и `DELETE` отдельного ресурса добавьте `/{uuid}`. Общие поля: `uuid`, `name`,
`description`, `project_id`, `created_at`, `updated_at`.

IAM-права: `exordos_s3.replication_target.{create,read,update,delete}` и
`exordos_s3.replication_rule.{create,read,update,delete}`. Манифест сервиса выдаёт
их существующей роли владельца проекта. Цель принадлежит проекту бакета,
правило — проекту цели.

## Поля цели

| Поле | По умолчанию | Значение |
| --- | --- | --- |
| `endpoint` | обязательно | HTTP(S) origin, например `https://backup.example:9000`; без пути, ключей в URL, query и fragment |
| `destination_bucket` | обязательно | Имя существующего бакета приёмника |
| `access_key` | обязательно | Ключ доступа к приёмнику; скрыт в GET и списках/фильтрах |
| `secret_key` | обязательно | Секрет приёмника; скрыт в GET и списках/фильтрах |
| `session_token` | `""` | Токен временных ключей; скрыт в GET и списках/фильтрах |
| `region` | `"us-east-1"` | Регион подписи запросов приёмника |
| `bucket_lookup` | `"auto"` | `auto`, `path` или `dns`; `path` подходит для endpoint без виртуальных хостов |
| `ca_cert_pem` | `""` | Пользовательские сертификаты доверия PEM, только для HTTPS |
| `storage_class` | `"STANDARD"` | Класс хранения объектов приёмника |
| `bandwidth_limit` | `0` | Байт/с; ноль отключает ограничение |
| `synchronous` | `false` | Нативный синхронный режим репликации RustFS |
| `disable_proxy` | `true` | Отключить чтение через прокси RustFS из этой цели |

Проверка TLS-сертификатов включена. API отклоняет IP-адреса loopback, link-local,
multicast и unspecified, а также origin `localhost`. Адреса частных сетей
разрешены. Пользователь выбирает endpoint без операторского списка разрешённых
адресов. Приёмник должен быть доступен с S3-нод. Проверка URL не проверяет
IP-адреса из DNS-ответов; оператор обеспечивает сетевую изоляцию исходящих
соединений S3-нод от служебных сетей, localhost и metadata-сервисов.

`endpoint`, `destination_bucket`, `region`, `storage_class` неизменяемы.
Для их смены удалите правила и цель и создайте новую. Остальные поля можно
обновлять, включая ключи. RustFS разрешает только одну цель с одинаковым
endpoint (хост и порт) на исходный бакет, даже при разных бакетах назначения.
API нормализует регистр хоста и стандартные порты.

Учётные данные хранятся в БД control plane и передаются S3-агенту для авторизации
RustFS на приёмнике. В отчёты агента, его метаданные и журнал репликации
`secret_key` и `session_token` не включаются. Ответы POST/PUT могут содержать
учётные данные; обрабатывайте их как чувствительные данные. RustFS сохраняет
собственные ключи remote target.
Шифрование объектов для недоверенного приёмника эта возможность не выполняет.

## Поля правила

| Поле | По умолчанию | Значение |
| --- | --- | --- |
| `enabled` | `true` | Включить правило; `false` приостанавливает его, сохраняя цель |
| `priority` | `1` | Положительное число, уникальное среди всех правил исходного бакета |
| `prefix` | `""` | Префикс ключей объектов; пустой соответствует всем ключам |
| `tags` | `{}` | Совпадение всех указанных тегов, объединённое с префиксом через AND |
| `replicate_existing` | `true` | Включить репликацию уже существующих подходящих объектов RustFS |
| `replicate_delete_markers` | `true` | Переносить versioned delete markers |
| `replicate_deletes` | `false` | Переносить удаление конкретных версий объектов |

Изменения метаданных полученных реплик не реплицируются (`ReplicaModifications`
всегда `Disabled`). Изменения метаданных обычных исходных объектов копируются
обычным образом.

В бакете допускается до 1000 правил Exordos. Ключи тегов: 1–128 символов,
значения: до 256. Для правил с фильтром по тегам явно задайте
`replicate_delete_markers=false`, иначе правило будет отклонено.
Для разных целей также нужны разные приоритеты.

Перенос существующих объектов выполняется фоновым сканером RustFS. Включение
правила не означает, что все старые объекты уже скопированы; длительность
зависит от объёма бакета и настроек сканера.

По умолчанию обычный DELETE источника передаёт marker на приёмник: объект
исчезает из обычного GET и списка объектов, предыдущие версии сохраняются.
Для восстановления удалённого объекта выбирайте version ID. Установите
`replicate_delete_markers=false`, чтобы удалённые объекты оставались видимыми
обычному GET. Оставьте `replicate_deletes=false`, чтобы удаление конкретной
версии на источнике не удаляло её на приёмнике. Включение этого флага позволяет
уничтожить историю приёмника. Lifecycle приёмника удаляет версии независимо
от репликации.
Синхронный режим сам по себе не подтверждает измеренный RPO или retention.

## Пример

Создайте бакет приёмника и включите его версионирование через собственный S3 API.
Ключам приёмника нужен доступ к бакету и его versioning для регистрации,
операциям с объектами, версиями и метаданными для выбранных правил. Точный набор
IAM-прав зависит от приёмника. Object lock и retention настраиваются отдельно
на приёмнике.

Включите версионирование существующего исходного бакета:

```http
PUT /v1/types/s3/instances/{instance}/buckets/{bucket}
Content-Type: application/json

{"versioning_enabled": true}
```

API не позволяет приостановить versioning, пока есть цели репликации
или на бакете включён Object Lock.
Создайте цель и сохраните её UUID из ответа:

```http
POST /v1/types/s3/instances/{instance}/buckets/{bucket}/replication_targets
Content-Type: application/json

{
  "name": "offsite",
  "endpoint": "https://backup.example:9000",
  "destination_bucket": "archive",
  "access_key": "replication-writer",
  "secret_key": "<destination secret>",
  "bucket_lookup": "path",
  "bandwidth_limit": 10485760
}
```

Добавьте правило:

```http
POST /v1/types/s3/instances/{instance}/buckets/{bucket}/replication_targets/{target}/rules
Content-Type: application/json

{
  "name": "photos",
  "priority": 10,
  "prefix": "photos/",
  "tags": {"backup": "yes"},
  "replicate_existing": true,
  "replicate_delete_markers": false,
  "replicate_deletes": false
}
```

Для другого префикса добавьте правило с приоритетом 20. Для второго приёмника
создайте цель с другим endpoint и правилами с ещё не занятыми приоритетами.
Для всего бакета используйте пустые префикс и теги.

Приостановка: `PUT .../rules/{rule}` с `{"enabled": false}`. Ротация ключей:
`PUT .../replication_targets/{target}` с `{"access_key": "new-key",
"secret_key": "<new secret>"}`. При ротации ARN нативной цели сохраняется.

Перед удалением цели удалите её правила. Удаление исходного бакета или инстанса
удаляет его ресурсы целей и правил Exordos. Удаление конфигурации репликации
не удаляет бакет приёмника и его объекты.

## Применение и эксплуатация

S3-агент регистрирует цели через admin API RustFS и применяет S3 replication XML.
В распределённом инстансе настройки применяет одна нода. Журнал сохраняет
соответствие UUID → ARN, незавершённые регистрации и ревизии ключей для повторных
попыток. Незавершённые регистрации содержат открытые настройки цели без секретов.
ID правил:
`exordos:{rule-uuid}`; этим пространством имён управляет Exordos. Чужие ID правил
и их XML-расширения сохраняются. Конфликт приоритета, несовместимый непустой Role
или уже зарегистрированная чужая цель на том же endpoint приводят к ошибке
применения без перезаписи чужой конфигурации.

Перед включением репликации через обновлённый CP обновите S3-агенты. Инстансы
без настроенной репликации сохраняют прежние поля и хеш целевых ресурсов: старые
агенты продолжают согласование, пока возможность не используется. Миграция
помечает существующие инстансы для пересоздания их target resources. Новые агенты
читают прежние метаданные. Перед приостановкой versioning агент убирает устаревшую
конфигурацию репликации, чтобы нативная проверка RustFS разрешила изменение.

Перед откатом плагина или миграции удалите правила и цели и дождитесь удаления
управляемой конфигурации RustFS агентами. Проверьте отсутствие правил `exordos:`
и связей в журнале. Downgrade миграции запрещён, пока есть строки целей; пустая БД
CP сама по себе не подтверждает завершение очистки DP. Откат кода до очистки
оставит работающую репликацию без управления CP.

Изменения применяются асинхронно. Успешный API-ответ подтверждает сохранение
желаемых настроек, но не доставку объектов. Агент сверяет фактические настройки
на следующих итерациях и повторяет неудачные попытки. Расхождение не позволяет
инстансу завершить согласование; проверяйте журнал S3-агента и метрики репликации
RustFS для исходного бакета. API прогресса/RPO отдельных правил нет.
[Описание мониторинга](monitoring.ru.md#репликация-бакетов) содержит метрики
и пояснения к разделу Replication в дашборде.

Не редактируйте ID правил Exordos и remote targets вручную. Потерянный журнал
восстанавливается из принадлежащих Exordos правил со ссылкой на нативный ARN.
Незавершённая регистрация записывается до запроса: при потере ответа повторная
попытка с сохранившимся журналом найдёт цель по открытым настройкам. Потеря журнала
при отсутствии такого правила требует вмешательства оператора. Exordos не
присваивает endpoint без принадлежащего ему правила или совпадающей незавершённой
регистрации. Согласовывайте внешние admin-изменения с Exordos: скрытые секреты
не позволяют отличить одновременно созданные одинаковые регистрации. Чужое
правило со ссылкой на удаляемую цель также запрещает удаление этой цели.
Изменённые в обход Exordos секреты нельзя проверить по редактированному списку
целей RustFS.

Запуск изолированного теста бэкенда:

```sh
EXORDOS_TEST_RUSTFS_BINARY=/path/to/rustfs-1.0.1 \
  .tox/py312/bin/python -m pytest exordos_s3/tests/integration/test_replication_rustfs.py
```

Дополнительно задайте
`EXORDOS_TEST_VICTORIAMETRICS_BINARY=/path/to/victoria-metrics-prod`, чтобы
проверить реальный OTLP-экспорт и все запросы панелей метрик Replication на
временном локальном хранилище метрик. Панель лога ошибок использует VictoriaLogs
и требует отдельной проверки. После теста процессы RustFS и VictoriaMetrics
останавливаются.

Проверка миграции, ORM CRUD и конкурентного создания приоритетов использует
уникальную временную схему PostgreSQL. Нужен URL с правом создания схем:

```sh
EXORDOS_TEST_POSTGRES_URL=postgresql://user@localhost/test_database \
  .tox/py312/bin/python -m pytest exordos_s3/tests/integration/test_replication_database.py
```
